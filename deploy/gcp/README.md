# Deploying CDN Manager on Google Cloud

The console runs on **Cloud Run**, backed by **Cloud SQL for PostgreSQL 16**. Passwords live in **Secret Manager**. **Cloud Build** builds the container, so Docker is not needed on your PC.

```
Browser / NOC  ──HTTPS──┐
Nodes (HMAC telemetry) ─┼─>  Cloud Run "cdnmanager"  ──Unix socket──>  Cloud SQL (PostgreSQL 16)
Middleware (API keys) ──┘     min 1 instance, CPU always on                 daily backups + PITR
                                   │
                              Secret Manager (DB password, first admin password)
```

| Resource | Default name | Notes |
| --- | --- | --- |
| Cloud Run service | `cdnmanager` | 1 vCPU, 1 GiB, 1 to 4 instances, region `asia-south1` (Mumbai) |
| Cloud Run job | `cdnmanager-migrate` | Runs `alembic upgrade head` before every deploy |
| Cloud SQL | `cdnmanager-pg` | `db-custom-1-3840`, 20 GB SSD that grows on its own, 14 daily backups, point-in-time recovery, deletion protection |
| Artifact Registry | `cdnmanager` | One image per build, tagged with the build id |
| Secrets | `cdnmanager-db-password`, `cdnmanager-admin-password` | Generated by `setup.sh` |
| Service account | `cdnmanager-run` | Only Cloud SQL Client and access to those two secrets |

Every name, the region, and the sizes are set in [config.sh](config.sh). Override any of them by exporting a variable before running a script, for example `REGION=asia-south2`.

## Before you start

- A Google Cloud project with billing turned on, and the Owner role on it (or Editor plus Security Admin).
- Nothing to install locally. Everything below runs in **Cloud Shell** (the `>_` button in the Cloud Console), which already has `gcloud`.

## 1. Bundle the code on this PC

In PowerShell, from `D:\Corpus\CDNManager`:

```powershell
powershell -ExecutionPolicy Bypass -File deploy\gcp\package.ps1
```

This writes `dist\cdnmanager-gcp.tar.gz` (about 60 KB). It contains the app, migrations, Dockerfile, and these scripts. Specs, documents, sample files, and the local SQLite database are left out.

## 2. Upload and unpack in Cloud Shell

In Cloud Shell, open the ⋮ menu, choose **Upload**, and pick `cdnmanager-gcp.tar.gz`. Then:

```bash
mkdir -p ~/cdnmanager && tar xzf ~/cdnmanager-gcp.tar.gz -C ~/cdnmanager && cd ~/cdnmanager
gcloud config set project YOUR_PROJECT_ID
```

## 3. One-time setup

```bash
bash deploy/gcp/setup.sh
```

This takes about 10 to 15 minutes; most of it is creating the database. It turns on the APIs, then creates the image repository, the Cloud SQL instance, database, and user, the two generated passwords, and the runtime service account. It also grants Cloud Build permission to deploy. It is safe to run again: anything that already exists is left alone.

## 4. Build and deploy

```bash
bash deploy/gcp/deploy.sh
```

Cloud Build builds the image, pushes it, runs the database migration job, and deploys the service. If the migration fails, the deploy stops and the running revision keeps serving. The script finishes by printing the service URL and the result of `/readyz`.

## 5. First sign-in

The first super admin is `admin` (set by `ADMIN_USERNAME`). Read the generated password with:

```bash
gcloud secrets versions access latest --secret=cdnmanager-admin-password
```

The admin is created only while the users table is empty. Later deploys never reset that password, and changing the secret afterwards has no effect. Create the NOC, support, billing, and tenant users from **Users** in the console. Production never loads the demo accounts or demo tenants.

## 6. Point nodes and middleware at it

- Node agents post telemetry to `https://<service-url>/api/v1/telemetry`. Each node needs its own signing secret, set when the node is added in the console.
- Middleware calls `/api/v1/sessions/register` and `/api/v1/edge-map` with the tenant API key.
- Requests reach the app over HTTPS only. Cloud Run redirects plain HTTP.

## Deploying updates

Run `package.ps1` on the PC again, upload the bundle, unpack it over `~/cdnmanager`, and run `bash deploy/gcp/deploy.sh`. Each deploy is a new Cloud Run revision, so rolling back is one command:

```bash
gcloud run revisions list --service=cdnmanager --region=asia-south1
gcloud run services update-traffic cdnmanager --region=asia-south1 --to-revisions=REVISION_NAME=100
```

Rolling back the app does not roll back a migration. Keep migrations additive (new columns and tables) so the previous revision still works against the newer schema.

### Deploy from GitHub on every push

[.github/workflows/deploy.yml](../../.github/workflows/deploy.yml) runs the tests on every push and pull request. On a push to `main` it also runs `cloudbuild.yaml`, the same build, migrate, and deploy that `deploy.sh` runs. GitHub signs in to Google Cloud with Workload Identity Federation, so no service-account key is stored in GitHub.

One-time, in Cloud Shell, after `setup.sh` (use GitHub's exact spelling of the repository, including case):

```bash
git clone https://github.com/OWNER/REPO.git ~/cdnmanager && cd ~/cdnmanager
bash deploy/gcp/setup.sh
GITHUB_REPO=OWNER/REPO bash deploy/gcp/github-setup.sh
```

`github-setup.sh` creates a `cdnmanager-deploy` service account that only the `main` branch of that repository can use. It prints four values; add them in GitHub under **Settings → Secrets and variables → Actions → Variables**: `GCP_PROJECT_ID`, `GCP_REGION`, `GCP_WIF_PROVIDER`, `GCP_DEPLOY_SA`. After that, each push to `main` deploys, and the run summary shows the service URL. You can also start a deploy by hand from the **Actions** tab (**Test and deploy → Run workflow**).

## Stopping and starting

```bash
bash deploy/gcp/control.sh status
bash deploy/gcp/control.sh stop
bash deploy/gcp/control.sh start
```

`stop` closes the app to outside traffic, scales it to zero instances, and stops the Cloud SQL instance. While stopped you pay only for database storage and backups (a few US dollars a month), and nodes cannot deliver telemetry. `start` brings the database up first, reopens the app, and waits until `/readyz` answers. Users, settings, and history are unchanged.

Start the app before pushing to `main`. A deploy runs the migration job, which cannot reach a stopped database.

## Operating it

| Task | Where |
| --- | --- |
| Logs | Cloud Run → `cdnmanager` → Logs. App lines are JSON with `severity`, so filters like `severity>=WARNING` work. |
| Health | `/readyz` checks the app and the database. (Cloud Run reserves `/healthz`, so that path returns Google's 404.) |
| Backups | Cloud SQL → Backups. Daily at 02:00 IST, 14 kept, with point-in-time recovery. |
| Restore a backup | Restore into a new instance, check it, then point `SQL_INSTANCE` at it and run `deploy.sh`. |
| Rotate the DB password | Add a new version of `cdnmanager-db-password`, run `gcloud sql users set-password cdnmanager --instance=cdnmanager-pg --password="$(gcloud secrets versions access latest --secret=cdnmanager-db-password)"`, then `deploy.sh`. |
| Custom domain | Cloud Run → Manage custom domains (or an external HTTPS load balancer). With a load balancer in front, set `TRUSTED_PROXY_HOPS=2` in `cloudbuild.yaml`. |
| High availability | `SQL_AVAILABILITY=REGIONAL` before `setup.sh` (a standby in a second zone; about twice the database cost). |

### Why these settings

- **Minimum one instance with CPU always on.** Offline detection (every 10 s), hourly usage-period finalisation, and retention run inside the app. Cloud Run's default throttles CPU between requests, which would stall them.
- **Several instances are safe.** Each background tick takes a PostgreSQL advisory lock, so only one instance runs it. The same lock makes sure only one instance creates the first admin.
- **Real client address.** The tenant IP allow list uses the address Google's front end appends to `X-Forwarded-For`. With `TRUSTED_PROXY_HOPS=1` the app reads only that last entry, so a caller cannot forge their address by sending the header themselves.
- **No Redis.** Login sessions are stored in PostgreSQL, which all instances share. Memorystore would add cost without changing behaviour.
- **Connections.** Each instance keeps up to 10 database connections (`DB_POOL_SIZE` + `DB_MAX_OVERFLOW`). With 4 instances that is 40, well inside the instance's limit. Raise `SQL_TIER` before raising `MAX_INSTANCES` much further.

## Cost

With the defaults the estimate is about **US$100–120 a month**: Cloud SQL around US$55 (1 vCPU, 3.75 GB, 20 GB SSD, backups) and Cloud Run around US$50 (one always-on instance). Check current prices for your region in the [Google Cloud pricing calculator](https://cloud.google.com/products/calculator). Regional database HA roughly doubles the Cloud SQL part.

## Removing everything

Cloud SQL has deletion protection on, so it cannot be deleted by accident. To remove it on purpose:

```bash
gcloud sql instances patch cdnmanager-pg --no-deletion-protection
gcloud sql instances delete cdnmanager-pg
gcloud run services delete cdnmanager --region=asia-south1
gcloud run jobs delete cdnmanager-migrate --region=asia-south1
gcloud artifacts repositories delete cdnmanager --location=asia-south1
gcloud secrets delete cdnmanager-db-password
gcloud secrets delete cdnmanager-admin-password
gcloud iam service-accounts delete cdnmanager-run@YOUR_PROJECT_ID.iam.gserviceaccount.com
```

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `setup.sh` stops at the Cloud SQL step with an edition or tier error | The tier is not offered in that region. Try `SQL_TIER=db-custom-2-7680`, or another region. |
| Build fails with `PERMISSION_DENIED` on deploy or `actAs` | The Cloud Build permission step in `setup.sh` did not run. Re-run `setup.sh`. |
| `migrate` step fails | Open the job's logs: Cloud Run → Jobs → `cdnmanager-migrate`. Usually the database password secret and the Cloud SQL user are out of step; re-run `setup.sh`, which re-applies the password. |
| Revision fails to start with "production needs PostgreSQL" | `DB_NAME` or `CLOUD_SQL_INSTANCE` is missing from the service's environment. Deploy with `deploy.sh` rather than by hand. |
| Sign-in loops back to the login page | The site was opened over plain HTTP through a proxy that strips HTTPS. Session cookies are HTTPS-only in production. |
| Dashboard stops updating and nodes show offline | Check that minimum instances is 1 and CPU is always allocated (Cloud Run → Edit → Container → CPU allocation). |
